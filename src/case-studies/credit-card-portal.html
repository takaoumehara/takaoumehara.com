Challenge 課題

The credit card portal had been built incrementally over years — same account data appearing in 3+ places with inconsistent patterns, 5+ clicks for basic tasks like making a payment, zero shared components. Service call volume climbed because users couldn't self-serve. The tension: customers needed trust and clarity in a financial interface — you're asking them to move their money — but the portal offered neither. Every feature had been designed in isolation. The constraint: fix it while building forward infrastructure, not just patching surfaces. クレジットカードポータルは何年もかけて段階的に構築された — 同じアカウントデータが 3 か所以上に異なるパターンで表示され、支払いなどの基本的なタスクに 5 回以上のクリックが必要で、共有コンポーネントはゼロ。ユーザーがセルフサービスできないため、サービスコールの量が増加した。緊張：顧客は金融インターフェースで信頼と明確さを必要としていた — あなたは彼らにお金を動かすよう頼んでいる — しかしポータルはどちらも提供しなかった。すべての機能が孤立して設計されていた。制約：表面にパッチを当てるだけでなく、前方インフラを構築しながら修正する。

Solution 解決策

I led a discovery audit that found the root cause wasn't cosmetic — there was zero design infrastructure. The fix worked at two levels: rebuild 4 priority flows (account setup, login, summary, payments) prioritized by frequency × pain severity for immediate impact, and build a 125+ component design system in 3 layers (Foundation tokens, Components, Patterns) to prevent recurrence. 105 high-fidelity screens (85 desktop, 20 mobile), 14 prototypes tested with stakeholders. The decisive move was treating the system as the actual deliverable, not just the flows. Service calls decreased in 2022 as streamlined flows removed friction. The mobile app team adopted the same system for v2.0. By 2023 it became the org-wide design standard. 私は発見監査を主導し、根本原因が外見的なものではないことを発見した — デザインインフラがゼロだった。修正は 2 つのレベルで機能した：4 つの優先フロー（アカウント設定、ログイン、サマリー、支払い）を頻度 × 痛みの重大度で優先して即座の影響のために再構築し、125 以上のコンポーネントデザインシステムを 3 層（基盤トークン、コンポーネント、パターン）で構築して再発を防ぐ。105 の高精細画面（85 デスクトップ、20 モバイル）、関係者とテストされた 14 のプロトタイプ。決定的な動きは、フローだけでなくシステムを実際の成果物として扱うことだった。2022 年に合理化されたフローが摩擦を取り除いたため、サービスコールが減少した。モバイルアプリチームは v2.0 で同じシステムを採用した。2023 年までに全社デザイン標準になった。

Two-Level Fix: Flows + System 2 レベルの修正：フロー + システム

The audit's finding wasn't a list of broken screens — it was that there was no shared component layer at all, so any fix would eventually regress. The response addressed both symptom and cause: rebuild the four priority flows that drove support calls, then build the infrastructure to prevent the same problem from recurring. 監査の発見は壊れた画面のリストではなかった — 共有コンポーネント層が全くなかったため、どんな修正も最終的には後退する。対応は症状と原因の両方に対処した：サポートコールを引き起こした 4 つの優先フローを再構築し、その後同じ問題が再発するのを防ぐためのインフラを構築する。
