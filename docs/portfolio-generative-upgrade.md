# 描画技術によるポートフォリオ「箱」のレベルアップ — 方向づけ

> Written by: superforge (superforge-ui) · 2026-08-06 · **検討のみ・未実装**
> 対象: 作品の中身ではなく、サイトそのもの（index / work / about / projects の器）

---

## 0. 結論を先に

提示された技術のうち、**このサイトで採用すべきは3つ、条件付きが2つ、却下が5つ**。

| | 技術 | 使いどころ | 判断 |
|---|---|---|---|
| 1 | **SVG + CSS/JS** | ケーススタディ内の図解を PNG → SVG 化 | **採用（最優先）** |
| 2 | **Canvas API（素）** | 生成OGP画像をビルド時に焼く | **採用** |
| 3 | **Canvas API（素）** | Playable カードのアートを「模造」から「本物の縮小版」へ | **採用** |
| 4 | SVG/JS | ヒーロー見出しがポインタに反応する | 条件付き |
| 5 | D3.js | 20年分の実践マップ（静止SVGとして焼く） | 条件付き・データ待ち |
| — | p5.js | 試作用ツールとしてのみ | 本番投入は却下 |
| — | GLSL / シェーダー | — | **却下** |
| — | Three.js | — | **却下** |
| — | PixiJS / Paper.js | — | **却下** |
| — | React Flow | — | **却下** |

却下が多いのは技術への評価ではなく、**このサイトが持っている資産を壊す**からです（§5）。

---

## 1. 判断の軸 — 「装飾」ではなく「証拠」として使えるか

ポートフォリオに描画技術を足す施策は、**足した瞬間に品質が下がる**ケースが最も多い領域です。
重くなり、モバイルで発熱し、採用担当は3秒でスクロールし、そして「どこかで見た画面」になる。

なので採否は1つの問いだけで決めています。

> **その描画は、JPEGでは代替できない仕事をしているか？**

- 代替できる（見た目が良くなるだけ）→ 却下。画像で足りる。
- 代替できない（言語が切り替わる／実物が動いている／データから生成される）→ 採用候補。

この軸で見ると、提示リストの上半分（p5・Three・シェーダー）はほぼ「代替できる」側、
下半分（SVG・Canvas・D3）が「代替できない」側に落ちます。**世間の人気とは逆順**です。

## 2. サイトの実態 — 効いてくる制約3つ

検討にあたって確認した、判断を左右する事実。

1. **ビルドステップが存在しない。** npm も bundler もなく、48ページすべてが
   `<style>` と `<script>` を内包した自己完結HTML。`python3 -m http.server` で開く。
   → これは負債ではなく**資産**。20年運用するポートフォリオとして、依存が腐らない構造。
   施策がこれを壊すなら、その施策は間違い。

2. **モーション語彙が既に規律を持っている。** `transform` / `opacity` のみ、
   `prefers-reduced-motion` で全停止（`index.html:1342`〜）。canvas も GPU ループも無し。
   → 新しい描画を足すなら**同じ規律に従わせる**のが条件。例外を作ると全体が崩れる。

3. **生成的な要素は既に入っている。** `index.html:1985`〜 でグラデーションのパレットを
   6プリセットからロードごとにランダム選択している。
   → ゼロからの導入ではなく**既にある方向の延長**として考えるべき。新奇性は要らない。

補足: 現在の Playable カードのアート（`.play-art--resona` 等）は
**CSSによる「模造」**です。バネが縮む円、引かれていく線 —
作品の挙動を *演じている* が、作品そのものではない。ここが §4-3 の出発点。

## 3. 採用 ①：ケーススタディの図解を SVG にする（最優先）

### 何をするか
現在 PNG で貼られている「主張を担っている図」を、テキストとパスを持つ SVG に置き換える。
写真は対象外。図だけ。

候補（既存アセットから）:
- Carnegie の PDSA フロー（`PDSAFlow-Horizontal01〜04.png`、`PDSA_Interaction_Flow.png`）
- XQ Canvas フレームワーク（`xq_map_v7-2.jpg`）
- Design Systems の3枚（`Designsystems.001〜003.png`）
- intentfirst の 8 Context Tokens

### なぜこのサイトでこそ成立するか
**このサイトはバイリンガルで、図の中の文字だけが翻訳されていない。**

日本語に切り替えると、本文は日本語になるのに、図の中は英語のまま残ります。
これは現状で最も大きな穴で、しかも PNG である限り**構造的に直せません**。
SVG にすれば `<text>` は既存の `html.lang-jp` トグルにそのまま乗ります。

派生して同時に解決すること:
- 拡大してもボケない（現在は Retina でも図の文字が甘い）
- 背景が透過するので、ダーク面／クリーム面のどちらに置いても馴染む
- 段階表示ができる（PDSA の4ステップを順に出す等）— これは PNG では不可能
- 図の中の文字が検索・読み上げの対象になる（スクリーンリーダーが図を読める）

### 技術・コスト・リスク
- **技術**: 素のSVG + 既存のCSS。ライブラリ **0**。ビルド変更 **なし**。
- **コスト**: 図1点あたり中（手作業でのトレース）。全部やらない。**主張を担っている図だけ**。
- **リスク**: 低。失敗しても PNG に戻すだけ。
- **やめる条件**: 図が複雑すぎて SVG が 100KB を超えるなら、その図は PNG のまま残す。

## 4. 採用 ②：生成 OGP 画像（実行時コスト 0）

### 現状の問題
48ページ中38ページに `og:image` がありますが、値が **相対パス**です。

```html
<meta property="og:image" content="../assets/cli-studios/CLI_UI_Screens.png">
```

OGP の仕様上、`og:image` は**絶対URL**である必要があります。
つまり **Slack / LinkedIn / X に貼っても画像が出ていない可能性が高い**。
（→ §7 の要確認事項。実際にクロールして確かめていません）

さらに、出ている場合も画像はバラバラで、共有面に統一されたブランドがありません。

### 提案
プロジェクト名を**種（seed）**にした決定論的な幾何グラフィックを生成し、
1200×630 の PNG として書き出して**コミットする**。実行時 JS はゼロ。

- 同じ名前からは常に同じ絵が出る（`hash("cli-studios")` → 角度・分割・色を決定）
- 48枚が**同じ設計言語で、かつ全部違う**
- 色は既存トークン（`--ink` `#121212` / クリーム `#f4efe4` / 暗面 `#0d0d0f` /
  アクセント `#9370f6` `#9ec5fe`）から外れない
- タイトル文字を焼き込むので、画像を用意していないページも成立する

### なぜこれが「箱のレベルアップ」として一番大きいか
**サイトに来る前に見られる面**だからです。
ヒーローの演出を磨いても、見るのは既に来た人だけ。OGP は共有されるたびに露出します。
効果 ÷ 実行時コスト の比が全案の中で最大。

### 技術・コスト・リスク
- **技術**: ローカルで node + 素のCanvas（または SVG を書いて PNG 化）。1回実行。
  **サイト本体には1バイトも足さない。**
- **コスト**: 生成スクリプト小 + 目視での品質確認。
- **リスク**: ほぼ無し。気に入らなければ生成物を消すだけ。
- **同時にやること**: 相対パス → 絶対URL の修正（これ単体でも価値がある）。

## 5. 採用 ③：Playable カードを「模造」から「実物の縮小版」へ

### 何をするか
`index.html` の `.play-art` は今、CSS でバネや線を**演じています**。
これを、その作品の挙動を実際に走らせる極小の Canvas に置き換える。

### なぜこのサイトでしか成立しないか
**本人の作品が、まさにその挙動そのものだから。**

Resona は擬似触覚、Rakugaki Jam は線が引かれて壁へ渡ること、
Typespace は文字が空間に散ること。
カードが「動くサムネイル」なのではなく、**カード自体が作品の証拠**になります。

インタラクティブな仕事をしている人のポートフォリオが静止画なのは、
それ自体が説得力の穴です。ここはその穴を塞ぐ、他の誰も真似できない一手。

### p5.js ではなく素の Canvas API を使う理由
p5.js は本体が MB 級です。カード4枚・各2秒の演出のために積むのは**逆方向**。
1カードあたり自前 1〜3KB 程度で足ります。

ただし **試作では p5 を使うべき**です。挙動を探るのは p5 が圧倒的に速い。
確定したものだけを素の Canvas に書き下ろす — これが正しい p5 の使い方。

### 守る条件（これを外すと必ず失敗する）
- `IntersectionObserver` で**画面外は完全停止**
- hover / focus の間だけ走らせる（常時ループしない）
- `prefers-reduced-motion` で1フレーム静止画
- **JS が無効・失敗しても現在のCSS版が残る**（段階的強化。canvas は上に重ねるだけ）
- `pointer: coarse`（タッチ）では静止画。モバイルで走らせない
- 1カード1挙動。2秒以内に1周。色は既存パレット

### リスク
中。**「動く＝良い」に流れると散らかる**のがこの案の唯一の危険です。
4枚全部を派手にすると、どれも見えなくなる。
1枚だけ本物にして残りをCSSのまま置く、という着地もあり得ます（むしろ推奨）。

## 6. 条件付き ①：ヒーロー見出しがポインタに反応する

PR #8 の「Open」に既出の案。「Intent first. Then the interface.」という見出しが、
カーソル（＝注意の位置）に反応する。**見出しの主張を見出し自体が実演する**構図。

筋は良い。ただし条件が厳しい。

- 見出しは常にプレーンな `<h1>` のまま。演出は別レイヤ
- タッチでは無効
- 効果は「文字が意図に反応する」1点に絞る。3つ足したら終わり
- **まず文字ごとの `<span>` + `transform` で試す。** Canvas も SVG filter も要らない可能性が高い
- **やめる条件**: 見出しの読了が 0.5 秒でも遅れたら中止

順序としては §5 の後。カードで手応えを得てからでいい。

## 7. 条件付き ②：20年分の「実践マップ」（D3）

### 何をするか
30数プロジェクトを、**共通する手法**で結んだ1枚の図。
Verizon / Carnegie / Kitadoko / intentfirst を貫いている方法論を可視化する。

### 価値
一覧ページでは構造的に言えないことが言えます。
「20年、いろいろやってきた人」ではなく「**一貫した方法を持っている人**」に見える。
about.html の主張を、文章ではなく形で証明できる唯一の手。

### ただし決定的な注意
**ネットワーク図は誰も操作しません。** 採用担当はスクロールして去ります。
なので「インタラクティブなグラフ」にしてはいけない。

→ **D3 は座標計算にだけ使い、結果を静止SVGとして焼いてコミットする。**
　 実行時に D3 をロードしない。§4 の OGP と同じ思想です。

### 前提（未整備）
プロジェクト間の「共通の手法」タグがまだ存在しません。
図を作る前に、**データが要る**。ここが実質のコスト。
`docs/portfolio-content-intake-prompt.md` の8章構成に手法タグを1項目足すのが自然な入口。

## 8. 却下と、その理由

| 技術 | 却下理由 |
|---|---|
| **GLSL / レイマーチング** | 2024年以降のポートフォリオで**最も既視感のある選択**。電池を食い、モバイルで発熱し、UXの実務について何も語らない。唯一成立するのは「シェーダーが作品そのもの」の場合だが、現状のカード群にそれは無い。「幻想的」は、この人の強みではない。 |
| **Three.js** | 空間の仕事（Kitadoko、Festival）はあるが、3D再現より**良い写真のほうが強い**。コストが1桁違う上、勝てない。 |
| **PixiJS** | 大量スプライトの高速描画が必要な場面が無い。素のCanvasで足りる規模。 |
| **Paper.js** | ベクター編集が必要な場面が無い。SVGで足りる。 |
| **React Flow** | React が無い。入れればビルドステップが要る。**このサイト最大の資産（ビルド不要・1ファイル完結）を捨てる**対価に見合わない。 |
| **p5.js（本番投入）** | 試作には最適。ただし本番に本体を積むのは過剰。**試作 p5 →本番 素Canvas** が正しい経路。 |

却下の共通項: いずれも「見た目が良くなる」だけで、**JPEGで代替できてしまう**。

## 9. ガードレール（採用する場合に必ず守ること）

1. **ビルドステップを増やさない。** 増やすなら生成物をコミットし、実行時は静的に保つ。
2. **段階的強化。** JS 無効・読み込み失敗で内容が消えない。
3. **`prefers-reduced-motion` で完全停止。** 現在の方針を例外なく維持。
4. **画面外は必ず停止。** `IntersectionObserver` を通さない常時ループを作らない。
5. **実行時JSに上限を決める。** 目安: トップページに追加する分は **15KB 未満（gzip前）**。
6. **モバイルは判定を `pointer: coarse` で行う。** 画面幅で判定しない。
7. **色は既存トークンから出ない。** 新しい色を持ち込む施策は、その時点で却下。

## 10. 順序

| # | 施策 | 効果 | リスク | 前提 |
|---|---|---|---|---|
| 1 | SVG 図解 | 高（バイリンガルの穴が塞がる） | 低 | なし |
| 2 | 生成OGP + 絶対URL修正 | 高（外向き最大） | 極小 | なし |
| 3 | Playable カード実物化 | 高（他が真似できない） | 中 | 各作品の挙動仕様 |
| 4 | ヒーローの反応 | 中 | 中 | 3の手応え |
| 5 | 実践マップ | 高（ただし遅効） | 中 | **手法タグのデータ整備** |

1 と 2 は独立していて、どちらからでも始められます。

## 11. 未確認・要判断

- **og:image の相対パス問題は実機で確認していない。** 実際に Slack / LinkedIn に貼って
  画像が出るか確かめる必要がある。出ていれば §4 の優先度は下がる（統一感の話だけになる）。
- **Playable 各作品の挙動仕様が手元にあるか不明。** Typespace / Resona の挙動を
  縮小再現するには、元の実装か挙動の記述が要る。無ければ §5 は「印象の再現」になり、
  それは今の CSS 版と本質的に変わらない — つまり**やる意味が薄れる**。
- **実践マップの手法タグは未定義。** 誰が定義するか（本人の判断が要る）。
- **どこまで動かしたいかの本人の好み。** 本ドキュメントは一貫して
  「控えめ・証拠として」に寄せている。もっと攻めた見え方を望むなら §8 の判断は変わる。
