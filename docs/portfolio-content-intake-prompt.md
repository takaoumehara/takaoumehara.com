# ポートフォリオ内容ヒアリング指示書（各プロジェクトのAIセッションに貼る用）

Updated: 2026-08-12 — **v3**。

## v2 からの差分（なぜ書き直したか）

v2 を配って埋まらなかった／間違って埋まった箇所を、実装側の事実と突き合わせて直した。

1. **Variant C が選択肢に無かった。** 仕様（`portfolio-template-system.md` §2-2）には
   A / B / C の3つがあるのに、プロンプトは A / B しか出していなかった。結果、スキル・
   ツール案件（本来3〜4枚）に9枚分の物語を書かせることになる。埋まらないのは当然で、
   これはプロンプト側の欠陥。**§0 を3択にした。**
2. **どのカテゴリーに置くかを聞いていなかった。** サイトは5カテゴリー構成になったので、
   カード1枚がどの索引ページに載るかは本人にしか決められない。**§1 に追加。**
3. **サムネイルを要求していなかった。** どの索引タイルも `assets/thumbs/<slug>.jpg`
   （760×570）を必ず使う。無いとタイルが組めない。**§8 に必須項目として追加。**
4. **数字に出典と日付を求めていなかった。** 実測/見込みの区別だけでは古い数字が生き残る
   （実例: superforge のスキル数が 12 のまま複数ページに残っていた）。**§9 で
   「出典＋確認日」を必須にした。** 日付が無い数字は載せない。
5. **出力先が決まっていなかった。** 「Markdownで出力」だけでは会話に流れて消える。
   **`portfolio-case-study-<projectname>/` に4ファイル**を書かせる形にした。
   特に `OPEN-QUESTIONS.md` — 「不明・要確認」が各所に散っていると本人が拾えない。

6. **「本人が撮影」で終わっていた。** 何をどう撮ればいいかが書かれていないので、
   撮影されないまま止まる。**§8 を在庫表から作業指示に変えた** — ③（本人が撮る）に
   した素材には、道具・手順・出力仕様・失敗しやすい点・所要時間を必ず書かせる。
   合わせて「AIがやってよい範囲」を狭く定義した（実機・人・空間・音・複数端末は全部③）。
   **迷ったら③**。AIが再現しようとすると、トークンを使ったうえで偽物ができるため。
   ②に振り分けたものも、勝手に生成せず**先に一覧で確認を取る**こと。
7. **複数端末の同時収録に答えが無かった。** スマホ操作→大画面が反応する作品は
   Interactive Experience の中心なのに、撮り方も再生方法も書いていなかった。
   **§8-3 に手順を追加**（2ソース＋同期マーカー→編集で1本に合成）。
   **§8-4 で「同期させない方が正しい場合」も明示**した。

その他: 見出しの文字数を**自己申告させる**（守られたか受け取り側で目視しなくて済む）、
EN/JP は翻訳ではなく**2本の原文**であると明記、却下される書き方を**プロンプト内に実例で**
入れた（失敗表は v2 では相手のAIに渡っていなかった）。

## これは何か

各プロジェクト（Rakugaki Jam、Koe Baku 等）を実際に作っているAIセッションは、そのプロジェクトの
中身を一番よく知っている。takaoumehara.com のケーススタディを書くたびに一から聞き出すのではなく、
**このプロンプトをそのプロジェクトのAIセッションに貼り付けて、内容を書き出させる**ためのテンプレート。

出力はそのまま takaoumehara.com のキーノート型ケーススタディのスライド構成に流し込める形式に
揃えてある。HTML組み込みは takaoumehara.com 側のセッションが行うので、ここで求めるのは
**文章とメディア素材リストのみ**。

**設計上の要点**: このサイトのケーススタディは「文章 → 段落 → 画像」ではなく、**1枚1メッセージの
スライドの積み重ね**になっている。だから普通のプロジェクト説明を書かせると使えない。各スライドの
「大見出し1行」と「短いリード1本」が要る。以下のフォーマットはそれを取りに行くためのもの。

参照実装: Variant A = `projects/cli-studios.html` / Variant B = `projects/verizon-ai-agents.html`
/ Variant C = `projects/superforge.html`

## 貼り付け用プロンプト（ここから下をコピーして相手のAIセッションに渡す）

````
あなたはこのプロジェクトの開発に携わってきたAIとして、プロジェクトの中身を一番理解している
立場です。このプロジェクトを個人ポートフォリオサイト（takaoumehara.com）のケーススタディとして
紹介するための文章素材とメディア素材リストを、以下のフォーマットに沿って書き出してください。

【成果物 — 会話で返さず、必ずファイルに書くこと】

リポジトリ直下に `portfolio-case-study-<projectname>/` というフォルダを作り
（`<projectname>` はこのプロジェクトの短い英小文字スラッグ。例: `rakugaki-jam`）、
次の4ファイルを置いてください。

  portfolio-case-study-<projectname>/
  ├── README.md           ← §1〜§12 を埋めたもの（本体）
  ├── OPEN-QUESTIONS.md   ← 「不明・要確認」を全部ここに集約（後述）
  ├── MEDIA.md            ← §8 の素材リストをチェックボックス形式で
  └── assets/             ← いま手元にあって、そのまま渡せるファイルの実体

**書き方の順序**: 一度に全部書こうとせず、§0〜§5 を書いてファイル保存 → §5.5〜§8 →
§9〜§12、の3回に分けて追記してください。長い指示は後半が雑になります。分けてください。

**OPEN-QUESTIONS.md について**: 「不明・要確認」と書いた項目は、README の該当箇所に
残したうえで、**全部このファイルにも集めて**ください。本人が一度に答えられる形にするのが
目的なので、各項目は「どのセクションの何か」「なぜ分からないか」「本人がどう答えれば
埋まるか」の3点を1行ずつ。これが散っていると、本人が拾い切れず埋まりません。

【このサイトのページ構造 — これを前提に書くこと】

ページは「1枚1メッセージのスライド」を縦に積んだ構成です。順番は固定：

  Hero（大見出し＋リード）→ Tension（課題の対比）→ Approach（意思決定）→
  Structure（旧構造→新構造）→ Evidence（証拠＝画面・図・動画）→
  Craft（判断と、採用しなかった案）→ Proof（成果）→ Retrospective（残った宿題）→
  Closing（締めの一文）

各スライドには「大きなセリフ体の見出し1行」と「短いリード1本」が必要です。
段落が長いと、このデザインでは成立しません。

【重要な原則】

- 知らない数字・日付・役割を推測で埋めない。わからない項目は "不明・要確認" と明記する。
- 誇張しない。実際にあった課題・決定・結果だけを書く。
- 英語(EN)と日本語(JP)の両方で書く。**これは翻訳ではありません。** サイトは
  `<span class="t-en">` と `<span class="t-jp">` を切り替えて表示するので、両方が
  それぞれ自然な原文である必要があります。同じ主張を、各言語で一番よく言える形で
  書いてください。直訳された日本語は、日本語話者にはすぐ分かります。
- 一人称視点（「私は〜を決めた」「私が設計した」）で書く。
- **見出しは指定の文字数を守り、その直後に実際の文字数を `（EN 54字 / JP 27字）` の
  形で書き添えること。** 長い見出しはこのデザインでは物理的に入りません。字数を
  書かせているのは、あなた自身に検算させるためです。
- 機密・NDAで書けないことがあれば、隠すのではなく「ここは一般化した」と明示する。

【提出前に必ず自分で確認すること】

- [ ] 見出しは全部、字数を書き添えたか。超過しているものは無いか
- [ ] EN と JP が両方あるか。片方だけの項目は無いか
- [ ] 数字には全部、出典と確認日が付いているか（§9）
- [ ] 「不明・要確認」は OPEN-QUESTIONS.md に全部転記したか
- [ ] §6.5 の「採用しなかった案」に、各案の**魅力**を書いたか

## 0. このプロジェクトの見せ方（最初に判定）— ここを間違えると後が全部ずれます

次の3つから1つ選び、理由を1行で書いてください。以降の分量が変わります。

- [ ] **A: 証拠先行型**（全8〜10枚）— 実際の画面・成果物・写真・動画が
      「見せられる形で」十分ある
- [ ] **B: 物語先行型**（全10〜14枚）— 見せられるビジュアルが乏しい
      （NDA、内部ツール、思考やプロセスが主役）。証拠は構造図・フロー図で作る
- [ ] **C: ツール紹介型**（全3〜4枚）— スキル・ライブラリ・CLI など、
      「何をするものか」と「どう動くか」が分かれば成立するもの。
      Hero → 仕組み（+図）→ 補足1枚 → Closing で終わり

判定の目安:
- 人に見せて恥ずかしくない実スクリーンショットや写真が **8枚以上**あれば **A**
- 成果物が「使う道具」であって、課題→再設計の物語が主役でないなら **C**
- それ以外、迷ったら **B**

**Cを選んだ場合は、§4 Tension・§5.5 Structure・§10 Retrospective を飛ばして
構いません。** その3つは再設計案件のための枠です。道具に無理やり物語を付けると
嘘になります。飛ばす場合は「Variant C のため省略」と1行書いてください。

**さらに重要 — ページが今は作れない場合は、そう言ってください。**
実素材も無く、図解にできる構造も無く、語れる判断も無い、という状態なら、
無理に埋めずに「現時点では素材不足。〇〇が揃えば書ける」と書いて提出してください。
中身の無いケーススタディは、載せないほうがましです。これは失格ではなく、正しい報告です。

- 本文（2〜3文。どういう状態になったか）:
- チップ3個:

## 5. Approach スライド ← 意思決定を1行に凝縮

- **大見出し（EN / JP + 字数）**: 全角20文字・英語40文字以内。自分の判断を言い切る短い一文。
  強調したい語を1つ `**強調**` で囲む。

  良い例: "Structure first, **then surface**." / "構造が先、**表面は後**。"

- **リード文（EN / JP）**: 3〜4文。何を検討し、なぜその判断をしたか。
  実装の手順説明ではなく「なぜ」に集中する。

## 5.5. Structure スライド ← 構造そのものを見せる。結果だけ書かない
（Variant C は省略可）

このサイトで一番よく落ちるスロットです。「4セクションにした」という**結果**は書けても、
「その前がどうだったか」が無いと、読み手は何が改善したのか判定できません。

- **再設計前の構造**（どちらか書ける方で。両方あればなお良い）:
  - 画面遷移／IAのツリー（親子関係が分かる形で。テキストの入れ子で構いません）:
  - そのツリーの何が壊れていたか（1〜2文。深すぎる・戻れない・同じに見える 等）:
- **再設計後の構造**:
  - 新しいツリー、または最上位セクションの一覧（各セクションに1行の役割説明）:
  - 命名を変えたものがあれば「旧 → 新」と、変えた理由:
- **この2つを並べたときに一番言いたいこと**（1文）:

【素材が無い場合】旧構造の図が残っていなくても、**記憶で構いません**。
「おそらくこうだった」と分かる範囲で書き、確信度を添えてください（例: 「3層だったのは確実、
4層目があったかは不確か」）。図はデザイン側でCSSで組むので、画像は不要です。

## 6.5. Craft スライド ← AIをどう使ったか、そして何を採用しなかったか

**まず判定してください。この案件でAI（生成AI・エージェント等）を制作プロセスで使いましたか。**

- [ ] **使った** → 下の「A」を書く
- [ ] **使っていない** → 下の「B」を書く。**これは弱点ではありません**。空欄にせず必ず埋めること

推測で「使った」ことにしないでください。年代的に使いようがない案件は、正直に B を選ぶこと。

**A（AIを使った場合）**
- AIに何をさせたか（具体的に。「壁打ち」のような曖昧語は避ける）:
- AIが出した案の**どこがダメだったか**（「平均的で綺麗な解」の何が足りなかったか）:
- そこに人間として何を足したか:
- 試した案の数と、選定の基準:

**B（AIを使っていない場合）**
- この案件の制作条件（年・チーム構成・使ったツール。単独作業なら「単独」と明記）:
- AIには出せなかったであろう判断は何か（1文）:

**A・B 共通 — ここが読み手に一番効きます**
- 検討したが**採用しなかった**選択肢を **2〜3個**。各項目:
  - 案の名前（10文字程度。例: 「見た目のリフレッシュ」）:
  - その案の**魅力**（なぜ一度は検討に値したか。1文）:
  - **捨てた理由**（1〜2文）:

※「魅力」を書かずに欠点だけ書くと、藁人形（最初から論外な案）に見えて逆効果です。
　「検討に値しなかった案」は、そもそも書かなくて構いません。

## 8. メディア素材リスト → `MEDIA.md` に書く

**この章の目的は「素材の在庫表」ではありません。本人が次に何をすればいいかが
分かる状態にすることです。** 「無い」で終わらせず、誰がどう作るかまで書いてください。

### 8-1. まず、誰がやるかを振り分ける

各素材を次の3つに振り分けます。**推測で振り分けないこと** — リポジトリを見て、
実際にファイルがあるかを確認してから書いてください。

- **① 既にある** — リポジトリ内やビルド成果物として実在する。パスを書く。
- **② AIができる** — 次のものだけ。これ以外を②にしないでください。
  - リポジトリにある画像の切り出し・リサイズ・書き出し
  - コードを実行して撮れるスクリーンショット（ローカルで起動できる場合のみ）
  - 構造図・フロー図（SVG/CSSで清書するので、元は文字で書けば十分）
- **③ 本人が撮る** — 実機・人・空間・音・複数端末が関わるもの全部。

**振り分けの原則 — 迷ったら③にしてください。**
AIが「それらしく再現」しようとすると、時間とトークンを使ったうえで**偽物ができます**。
本物でないUIスクリーンショットは、このサイトでは使えません（実画面のみという決まりです）。
無いものは「無い」と正直に書くほうが、はるかに速く前に進みます。

**②に振り分けたものは、勝手に大量生成しないでください。**
「これとこれは私が作れます。作りますか？」と**一覧で確認を取ってから**着手すること。
不要な生成はコストになります。本人が「お願い」と言ってから作ってください。

### 8-2. ③（本人が撮る）には、必ず撮影指示を書く

「本人が撮影」とだけ書かれても、何をどう撮ればいいか分かりません。
**③にした素材ひとつひとつに、次の6項目を書いてください。**

```
【撮影指示】<素材名>
- 何を写すか   : （1行。画面のどの状態か、誰の何の動作か）
- 使う道具     : （iPhoneの画面収録 / QuickTime / OBS / カメラ+三脚 など具体名）
- 手順         : （番号付き。5ステップ以内）
- 出力         : （解像度・比率・尺の目安・ファイル名）
- 失敗しやすい点: （1行。これを外すと撮り直しになる、という点）
- 所要時間の目安: （5分 / 30分 / 半日 のいずれか）
```

道具は**本人が持っているものだけ**書いてください。持っていない機材を前提にした指示は、
撮影されないまま止まります。分からなければ「使える機材を確認したい」と
OPEN-QUESTIONS.md に書いてください。

### 8-3. 複数端末が関わる収録（スマホ操作 → 大画面が反応する作品）

Interactive Experience 系で必ず出てくる、いちばん難しいケースです。
**先に結論: 2本を同時再生して同期させようとしないでください。編集で1本に合成します。**

理由: ページ上の2つのプレイヤーは同期しません。それぞれが独立に読み込み・バッファ
するので、再生開始のズレは端末とネットワークで毎回変わります。JavaScript で
補正しても、モバイルでは片方だけ止まることがあります。**1本の動画ファイルに
してしまえば、同期は編集時に一度解決すれば永久に正しく、JSも要りません。**

撮り方（2ソース → 1本）:

1. **ソースA = スマホの画面**。iOS ならコントロールセンターの画面収録、
   Android なら標準の画面録画。操作している側が見ているものを撮ります。
2. **ソースB = 大画面**。次のどちらか。
   - 壁に映している側のPCを画面収録（Mac は QuickTime の新規画面収録、または OBS）
     — 画面の中身をきれいに見せたい場合はこちら。
   - 実際の投影を三脚のカメラ/別のスマホで撮る
     — 「その場の人が反応している」ことが主張なら、断然こちら。
3. **同期マーカーを最初に入れる。ここが一番重要です。**
   録画を両方回し始めたあと、**両方の記録に同時に現れる一瞬の出来事**を1回作ります。
   例: スマホを1回タップして、壁に特徴的な線が出る瞬間。あるいは画面が見える位置で
   1回手を叩く。編集ではこのフレームで頭を揃えます。これが無いと、後から
   合わせる基準が無く、目分量になります。
4. **合成する**。大画面を主、スマホを小窓（右下など）で重ねる。
   あるいは縦並びの分割。**書き出しは1ファイル**。
5. 音は、無音でも成立する作品なら**無音で書き出す**ほうが安全です
   （自動再生の制約が緩く、会場のノイズも入りません）。

出力仕様: 9:16（縦）または 16:9（横）どちらか一方に統一。尺は **20〜40秒**。
長いと最後まで見られません。ファイル名は `<slug>-composite.mp4`。

### 8-4. 「同期させない」ほうが正しい場合もあります

**旧版と新版の比較**（Before / After）は、**2本を別々に置くのが正解**です。
見る人が自分のペースで、行ったり来たりしながら見比べるからです。同期させると
かえって不便になります。現在 `projects/cli-studios.html` がこの形（9:16 を2本、
それぞれ独立して再生）で、これは意図的な設計です。

つまり:
- **同時性そのものが主張**（スマホを触ると壁が反応する）→ **1本に合成**
- **比較が主張**（前はこうだった、今はこう）→ **2本のまま並べる**

どちらなのかを §7 Evidence に1行で書いてください。

### 8-5. 素材の一覧

各項目について ① / ② / ③ を明記し、③には 8-2 の撮影指示を付けてください。

- **サムネイル（必須。これが無いと索引ページにカードを置けません）**:
  `assets/thumbs/<slug>.jpg` · **760×570（4:3）** · プロジェクトが一目で分かる1枚。
  実画面から切り出せるならそれが最良。無ければ「無い」と書いてください（代替を作ります）。
- Hero背景画像（横長。暗いスクリムを重ねるので、明るく細部が多い画像で可）:
- UI screenshot（実際の画面。**本物のみ**。モックアップ画像で代用しない）:
- Dark UI shot（黒背景のUI。あれば）:
- Photo（4:3。人が使っている様子・実機写真など）:
- Diagram（構造図・フロー図。文字で書けば十分。清書はこちらでやります）:
- 動画（8-3 / 8-4 のどちらの型か明記。ポスター画像も要ります）:
- Brand asset（ロゴ・アイコン・成果物のページなど）:

各項目ごとに:
- 素材の有無: [既存あり（枚数も） / 無い]
- 誰がやるか: [① 既にある / ② AIができる / ③ 本人が撮る]

**①のものは、`portfolio-case-study-<projectname>/assets/` に実体をコピーしてください。**
（容量が大きすぎるものはパスだけで構いません）

**最後に、③だけを抜き出した「本人のTODO」を MEDIA.md の先頭に置いてください。**
所要時間の合計も書いてください。ここだけ見れば作業が始められる状態にするためです。

## 9. Proof（成果）— 数字はページ全体でここ1回だけ

- 数値化できる成果を**最大3つ**（大きい数字 + 1〜2行の説明）。無理に数字を作らない。
- **各数字に、次の3つを必ず添えること。1つでも欠ける数字は載せません。**
  - 実測 か 見込み か
  - **出典**（どこで測ったか。ログ・アナリティクス・クライアント報告・自分の計測 等）
  - **確認日**（YYYY-MM-DD。いつ時点の数字か）

  ※ 出典と日付を求めているのは、数字が古びるからです。実際にこのサイトでは、
  　 ある道具の個数が増えた後も古い数のまま複数ページに残っていました。
  　 日付があれば、後から検算できます。

- **数字が無い場合でも、次の1文は必ず書く**:
  「この設計は、**誰の・何を**動かしたか」（何時間／何ドル／どの判断／誰の仕事、のどれか）。
  例: 「42人のデザイナーが、毎週2時間かけていた作業をやめられた」
  ※ 出典の言えない数字は入れないこと。言えないなら数字を外した形で1文にする。
- 上が書けたうえで、定性的な証明があれば追加（採用された・使われ続けている・
  フィードバック・受賞・次の仕事に繋がった 等）。

## 10. Retrospective スライド ← 決着しなかったことを書く
（Variant C は省略可）

成果の欄には書けないが、この仕事で残ったことを **2〜3個**。**うち最低1つは
「うまくいかなかったこと」または「まだ答えを持っていないこと」を必ず入れる**こと。

各項目:
- 見出し（全角25文字・英語50文字以内 + 字数。言い切る）:
- 本文（2〜3文。なぜそれが残ったか）:

書きやすい切り口（当てはまるものがあれば）:
- 出した数字が見込みのままで、実測に戻れていない
- 判断は正しかったと思うが、通すのに条件（時間・座組）が必要だった
- 納品後に自分の手を離れた部分があり、実際どうなったか確認できていない
- 順序を逆にしていたら違う結論になったかもしれない工程がある

**無理にひねり出さないこと。** 本当に2つしか無ければ2つで構いません。
ただし「特に無い」は不可 — その場合は「まだ振り返れるほど時間が経っていない」と書く。

## これは却下されます（実際に起きた例）

以下の書き方で出すと、こちら側で書き直しになります。先に避けてください。

| 出してはいけないもの | なぜダメか | 代わりに |
|---|---|---|
| "本プロジェクトをリニューアルしました" | 何が変わったか言っていない | 変化を主語にする（Before → After） |
| "UXが大幅に向上" | 測っていない主張 | 誰の何が変わったかを1文で。数字は出典付きのみ |
| "パフォーマンスを40%改善"（出典なし） | 検算できない | 出典と確認日を添える。無いなら数字を消す |
| 画像を10枚フラットに列挙 | §7 のグループ化を飛ばしている | 2〜4グループにまとめ、各グループに見出し |
| 採用しなかった案が全部ダメな案 | 藁人形になり、判断力が伝わらない | 各案の「一度は検討に値した理由」を書く |

| 旧構造が「複雑だった」の1行 | 読み手が改善を判定できない | 入れ子のテキストで階層を書く。記憶で可 |
| 英文を機械翻訳した日本語 | 日本語話者にすぐ分かる | 同じ主張を、日本語で一番よく言える形に書き直す |
| 見出しが指定字数の2倍 | デザインに物理的に入らない | 字数を書き添えて自分で検算する |
| "本人が撮影"だけで終わっている | 何をどう撮るか分からず止まる | §8-2 の6項目（道具・手順・出力・失敗点・所要時間）を書く |
| 実機の写真をAIが生成しようとする | 偽物になり、このサイトでは使えない | ③に回す。無いものは「無い」と書く |
| 動画を2本並べて「同期再生」と書く | プレイヤーは同期しない | §8-3。合成して1本にするか、§8-4 で別々に置く |
````

## 受け取った後の使い方（自分用メモ）

1. 各プロジェクトのAIセッションにこのプロンプトを貼って出力をもらう。
   成果物は `portfolio-case-study-<slug>/` フォルダ（4ファイル）。
2. **まず `OPEN-QUESTIONS.md` を開く。** ここに答えるのが最短経路。
   本人にしか答えられないことだけが集まっているはず。
3. **セクション0の判定**を確認 → A / B / C で組み方が変わる。
   判定基準は `docs/portfolio-template-system.md` §2-2。
   **C なのに9枚分の物語が書かれていたら、判定が間違っている。** 聞き直す。
4. **`MEDIA.md` の先頭に「本人のTODO」と所要時間の合計があるはず。** そこだけ見て着手する。
   撮影指示が6項目揃っていない項目があれば、そこだけ書き直させる（そのまま渡されても撮れない）。
   サムネイル（760×570）が無いと索引ページにカードを置けないので、これを最優先。
   **②（AIができる）に振り分けられたものは、必要なものだけ選んで発注する。** 一覧で
   聞いてくるはずなので、要らないものは断ってよい。
5. **§6.5 の判定（AIを使ったか）**を確認する。「使った」なのに中身が薄い場合は、
   AIの出力の何がダメだったかを1往復で聞き直す。ここが薄いページは判断の可視化ができない。
6. **§9 の数字に出典と日付があるか確認する。** 欠けている数字は載せない。
   ここを妥協すると、後で古い数字がサイト中に残る。
7. 集まった文章と素材を takaoumehara.com 側のセッションに渡す。スパインの各スロットは
   このヒアリング項目と1:1対応しているので、そのまま流し込める。
8. `§1 の掲載カテゴリー` に従って、該当索引ページ（`interactive.html` / `ai-products.html`
   / `ai-tools.html` / `work.html` / `brand.html`）にカードを追加し、
   `index.html` の該当カテゴリーの件数を更新する。**テストが件数を検証しているので、
   ここを忘れるとテストが落ちて気づける。**
9. アクセント色は §12 の表で重複を確認してから確定する。

### それでも出力が使えないとき

v3 はこの表の内容をプロンプト本体にも入れてあるので発生頻度は下がるはずだが、残る場合:

| 症状 | 原因 | 対処 |
|---|---|---|
| 見出しが長くて入らない | 字数の自己申告を飛ばされた | 該当スロットだけ「全角◯文字以内で3案・字数付き」と再依頼 |
| ツール案件なのに物語が長い | §0 で C を選ばなかった | 「Variant C で書き直して」とだけ言う |
| カテゴリーが空欄 | §1 を飛ばされた | 5択を再提示する。ここは本人判断でも可 |
| 数字に日付が無い | §9 の3点セットを飛ばされた | 「日付の無い数字は全部消して」と指示 |
| OPEN-QUESTIONS が空 | 全部埋めたつもりになっている | 「推測で埋めた箇所を全部ここに出して」と指示 |
