# ポートフォリオ内容ヒアリング指示書（各プロジェクトのAIセッションに貼る用）

Updated: 2026-08-03 — CLI Studios v2 と Verizon AI Agents の実装から得た要件を反映。

Previous update: 2026-08-02 — `docs/portfolio-template-system.md` のテンプレート体系（1つの物語スパイン
＋2つの証拠モード）に合わせて全面改訂。旧版はスロットの半分しか埋まらなかった。

## これは何か

各プロジェクト（Rakugaki Jam、Koe Baku 等）を実際に作っているAIセッションは、そのプロジェクトの
中身を一番よく知っている。takaoumehara.com のケーススタディを書くたびに一から聞き出すのではなく、
**このプロンプトをそのプロジェクトのAIセッションに貼り付けて、内容を書き出させる**ためのテンプレート。

出力はそのまま takaoumehara.com のキーノート型ケーススタディ（お手本＝`projects/cli-studios.html`）
のスライド構成に流し込める形式に揃えてある。HTML組み込みは takaoumehara.com 側のセッションが行うので、
ここで求めるのは**文章とメディア素材リストのみ**。

**設計上の要点**: このサイトのケーススタディは「文章 → 段落 → 画像」ではなく、**1枚1メッセージの
スライドの積み重ね**になっている。だから普通のプロジェクト説明を書かせると使えない。各スライドの
「大見出し1行」と「短いリード1本」が要る。以下のフォーマットはそれを取りに行くためのもの。

## 貼り付け用プロンプト（ここから下をコピーして相手のAIセッションに渡す）

````
あなたはこのプロジェクトの開発に携わってきたAIとして、プロジェクトの中身を一番理解している立場です。
このプロジェクトを個人ポートフォリオサイト（takaoumehara.com）のケーススタディとして紹介するための
文章素材とメディア素材リストを、以下のフォーマットに沿って書き出してください。

【このサイトのページ構造 — これを前提に書くこと】
ページは「1枚1メッセージのスライド」を縦に積んだ構成です。順番は固定：
  Hero（大見出し＋リード）→ Tension（課題の対比）→ Approach（意思決定）→
  Structure（情報・ワークフローの構造）→ Evidence（証拠＝画面・図・動画）→
  Craft（人間の判断とAI協働）→ Proof（成果）→ Retrospective（振り返り）→ Closing（締めの一文）
各スライドには「大きなセリフ体の見出し1行」と「短いリード1本」が必要です。
段落が長いと、このデザインでは成立しません。

【重要な原則】
- 知らない数字・日付・役割を推測で埋めない。わからない項目は "不明・要確認" と明記する。
- 誇張しない。実際にあった課題・決定・結果だけを書く。
- 英語(EN)と日本語(JP)の両方で書く（サイトはバイリンガル表示のため）。
- 一人称視点（「私は〜を決めた」「私が設計した」）で書く。
- 見出しは指定の文字数を守る。長い見出しはこのデザインでは物理的に入らない。
- **見出しは格好よさより明確さを優先する。** 比喩・標語・言葉遊びではなく、「誰が／何を／どうした」「何が分かる」をストレートに書く。
- 製品・AIツールの場合は、名前の由来より先に **入力、処理、出力、利用者** を説明する。Gem、NotebookLM、MCP等の実装方式も具体的に書く。
- 機密・NDAで書けないことがあれば、隠すのではなく「ここは一般化した」と明示する。

## 0. このプロジェクトの見せ方（最初に判定）

次のどちらかを選び、理由を1行で書いてください。以降の書き方が変わります。

- [ ] **A: 証拠先行型** — 実際の画面・成果物・写真・動画が「見せられる形で」十分ある
- [ ] **B: 物語先行型** — 見せられるビジュアルが乏しい（NDA、内部ツール、思考やプロセスが主役）

判定の目安：人に見せて恥ずかしくない実スクリーンショットや写真が **8枚以上**あれば A。
なければ B。迷ったら B（Bは図解で成立させる方針なので、素材不足で破綻しない）。

## 1. 基本情報
- プロジェクト名（EN / JP）:
- クライアント/対象（自主開発なら "Personal Project"）:
- 自分の役割（例: Lead Designer, Full-stack Developer, Prompt Engineer）:
- 制作年・期間:
- 公開リンク（公開URL, リポジトリ, デモ動画など。無ければ「無し」）:
- 機密上の制約（NDA等で書けない範囲があれば具体的に。無ければ「無し」）:

## 2. 一覧カード用の要約
- カード用タイトル（短縮版・全角12文字/英語25文字以内）:
- カテゴリタグ（2〜3個。例: "App Design", "AI Product", "Design System"）:
- 1文の説明（成果が伝わる書き方）:

## 3. Hero スライド ← ページの顔。ここが一番重要
- **大見出し（EN / JP 両方）**: 全角30文字・英語60文字以内。
  原則として **「何が変わったか」** を主語にする。AIツール紹介では例外として、最初に「そのツールが何をするか」を具体的に言い切る。
  文中で一番強い単語を1つだけ `**強調**` で囲む（デザイン側で色をつけるため）。
  良い例: "Five usability problems. One root cause. A redesign that started with **structure**."
  悪い例: "CLI Studiosのアプリをリニューアルしました"（何が変わったか言っていない）
- **リード文（EN / JP）**: 3〜4文。誰の何を、どう変えたか。数字があれば1つだけ入れる。
- **チップ**（3個・各10文字以内。技術や領域のラベル）:

## 4. Tension スライド ← 「前」と「後」の2枚を対比で書く
「前」側:
- タグ（例: "Where it started" / "出発点"）:
- 見出し（全角15文字・英語30文字以内。状態を言い切る）:
- 本文（2〜3文。何が壊れていたか、なぜ放置できなかったか）:
- チップ3個（症状を短く。例: "モーダル過多" "崩れたIA" "戻れない"）:

「後」側:
- タグ（例: "What it became" / "再設計後の姿"）:
- 見出し（全角15文字・英語30文字以内）:
- 本文（2〜3文。どういう状態になったか）:
- チップ3個:

## 5. Approach スライド ← 意思決定を1行に凝縮
- **大見出し（EN / JP）**: 全角20文字・英語40文字以内。自分の判断を言い切る短い一文。
  強調したい語を1つ `**強調**` で囲む。
  良い例: "Structure first, **then surface**." / "構造が先、**表面は後**。"
- **リード文（EN / JP）**: 3〜4文。何を検討し、何を捨て、なぜその判断をしたか。
  実装の手順説明ではなく「なぜ」に集中する。
- 検討したが**採用しなかった**選択肢と、その理由（1〜2個。回答はセクション7の Craft に配置する）:

## 6. Problems / Moves スライド（該当する方を1つ、または両方）
- **Problems 型**（課題→解決のペアが2〜5個ある場合）:
  各項目: 課題（1行）→ 解決（1〜2行）
- **Moves 型**（順を追った意思決定・工程が2〜4段ある場合）:
  各項目: ラベル（例: "01 リサーチ"）／見出し（1行）／説明（2〜3文）

## 6.5 Structure（構造）— システムや意思決定の関係を図にする
- 変更前の情報構造、業務フロー、またはシステム構成（ノードと接続を具体的に）:
- 変更後の構造（ノードと接続を具体的に）:
- **データ／知識／作業がどこからどこへ流れるか**（矢印の向きまで書く）:
- 入力 → 処理 → 出力 → 利用者を1行ずつ:
- 図の見出し（比喩ではなく、図が示す関係をそのまま書く）:

AIシステムの場合は、モデル名だけで済ませず、Gem / NotebookLM / Drive / MCP / APIなど各要素の役割と、
どの情報がどの要素へ渡るかを書く。複数の知識源が1つのハブへ統合される場合は、その関係を明記する。

## 7. Craft（判断とAI協働）
まず、この制作でAIを実際に使用したかを `[使用した / 使用していない]` で答える。推測は禁止。

**AIを使用した場合:**
- AIに任せた工程と、その具体的な入力・出力:
- 人間が保持した判断・編集・品質基準:
- AIの最初の出力で不十分だった点と、どう修正したか:
- 採用しなかったAI案／別方式と理由（最大3つ）:
- 使用したモデル・製品・接続方式（分かる範囲で具体的に）:

**AIを使用していない場合:**
- 一人／チーム、使用ツール、制約:
- 採用しなかった案と理由（最大3つ）:
- 人間として最も難しかった判断と、その判断基準:

## 8. Evidence（証拠）— スライドのグループ単位で書く ★メディア素材リストと対で答える
証拠は「画像を並べる」のではなく、**2〜4個のグループ**にまとめ、各グループを1スライドにします。
グループごとに:
- グループ名（例: "調査" "再設計した画面" "デザインシステム"）:
- そのグループの見出し（全角20文字・英語40文字以内）:
- そのグループのリード文（1〜2文。この証拠が何を証明しているか）:
- 含まれる素材（セクション9の項目と対応させる）:

【判定Bを選んだ場合】実素材の代わりに、次のどれで証拠を作れるか書いてください:
- 構造図・フロー図で説明できるもの（何を図解すべきか、1〜3個）:
- ビフォー/アフターの工程比較（表や帯で表現できるもの）:
- 数字・スケールを示すもの:

## 9. メディア素材リスト
各項目について「① 既にある」「② AIが今から生成できる」「③ 本人が新たに撮影/収録する必要がある」
のどれかを必ず明記すること。**「無い」を隠さないこと** — 無いと分かればデザイン側で代替できます。

- Hero背景画像（横長。暗いスクリムを重ねるので、明るく細部が多い画像で可）:
- UI screenshot（実際の画面。**本物のみ**。モックアップ画像で代用しない）:
- Dark UI shot（黒背景のUI。あれば）:
- Photo（4:3。人が使っている様子・実機写真など）:
- Diagram（構造図・フロー図。AIが清書しやすい）:
- Before/After動画（9:16の操作録画2本。YouTube限定公開が前提）:
- Brand asset（ロゴ・アイコン・成果物のページなど）:

各項目ごとに:
- 素材の有無: [既存あり（枚数も） / 無い]
- 取得方法: [AIが生成する / 本人が撮影・収録する / 未定なので相談]
- ファイルの場所（リポジトリ内のパス等、分かれば）:

## 10. Proof（成果）— 数字はページ全体でここ1回だけ
- 数値化できる成果を**最大3つ**（大きい数字 + 1〜2行の説明）。無理に数字を作らない。
- 数字が無い場合も、「この設計が **誰の、どの作業・判断・時間・リスク** をどう変えたか」を1文で言い切る。
- そのうえで定性的な証明を最大3つ（採用された、使われ続けている、意思決定に使われた、フィードバック等）。
- 使った技術・ツール・手法をタグ的に列挙:

## 11. Retrospective（振り返り）
- うまくいかなかったこと、または期待どおりでなかったこと（最低1つ）:
- 今も残る制約・未解決の論点（最大2つ）:
- もう一度やるなら変えること:
- 各項目は1〜2文。成功談に言い換えず、事実をストレートに書く。

## 12. Closing（締めの一文）
- **見出し（EN / JP）**: 全角25文字・英語50文字以内。この仕事から言える普遍的なこと。
  強調語を1つ `**強調**` で囲む。
  例: "Fix the structure, and **the surface follows**." / "構造を直せば、**表面はついてくる**。"

## 13. アクセント色（任意）
このプロジェクトに合う色があれば1つ選んでください。無ければ「おまかせ」。
青 / 緑 / オレンジ / 黄 / 紫 / ティール
````

## 受け取った後の使い方（自分用メモ）

1. 各プロジェクトのAIセッションにこのプロンプトを貼って出力をもらう。
2. **セクション0の判定**を確認 → A なら Variant A（証拠先行）、B なら Variant B（物語先行）で組む。
   判定基準は `docs/portfolio-template-system.md` §2-2。
3. **セクション9**を見て、「③本人が撮影」の項目だけ先に自分でスクショ/画面収録する。
   ここが最短経路のボトルネックになりやすいので、他の作業より先に着手する。
4. 集まった文章と素材を takaoumehara.com 側のセッションに渡す。スパインの各スロットは
   このヒアリング項目と1:1対応しているので、そのまま流し込める。
5. アクセント色は `docs/portfolio-template-system.md` §2-4 の割当表で重複を確認してから確定する。

### よくある失敗（AIの出力が使えないとき）

| 症状 | 原因 | 対処 |
|---|---|---|
| 見出しが長くて入らない | 文字数制約を無視された | 該当スロットだけ「全角◯文字以内で3案」と再依頼 |
| 「何を作ったか」しか書いてない | Heroの主語が変化になっていない | "Before → After" を明示して書き直させる |
| 数字が盛られている | 推測で埋めた | 「出典が言えない数字は全部消して」と指示 |
| 証拠が画像の羅列 | セクション8のグループ化を飛ばされた | グループ名と見出しだけ再依頼 |
