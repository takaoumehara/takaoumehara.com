AI Window Deck · Chrome Extension · 2026 AI Window Deck · Chrome拡張機能 · 2026

A layout you can see, not a form you have to fill in. 入力する設定画面から、見て置くキャンバスへ。

Dozens of tabs across several monitors, and the only way to place them was to type numbers into a form — a form that wiped every window already registered. I rebuilt the setup screen as a two-pane canvas: real monitors on the left, a live split grid on the right, drag a window onto a cell to assign it. Registration moved into its own modal, so saved work is never overwritten again. 複数ディスプレイに散らばる大量のタブを配置する手段が、フォームへの数値入力しか無かった。しかもその画面は、開くたびに登録済みのウィンドウを全消去した。私は設定画面を2カラムのキャンバスに作り直した — 左に実在のモニター、右にライブの分割グリッド、枠へドラッグすれば割り付く。登録はモーダルに分離し、保存済みのデータが上書きされることは無くなった。

Where it started 出発点

A form that erased your work 開くたびに消える設定画面

Opening the settings screen wiped everything already registered, so each session began by pasting the same list back in from a text file. In the popup the same layout collapsed to a 200px column, stacking every control on top of the next. 設定画面を開くたびに登録済みの内容が全消去され、毎回テキストファイルから同じリストを貼り直すところから始まった。ポップアップ表示では同じレイアウトが幅200pxに潰れ、要素が縦一列に折り重なった。

What it became 再設計後の姿

A canvas you drag onto 手で置ける、生きたキャンバス

Pick a monitor that actually exists, open the accordion library, drag a window onto a cell. Adding windows happens in its own modal — one at a time or pasted in bulk — so nothing already saved is touched. 実在するモニターを選び、アコーディオンのライブラリから枠へドラッグする。ウィンドウの追加は専用のモーダルで — 1件ずつでも一括貼り付けでも — 行うので、保存済みのものには一切触れない。

My approach アプローチ

Visual first, dynamic after. 視覚が先、自動適合は後。

Nobody wanted a numeric form; they wanted to see their own screens and the shape of the windows on them. So I made the physical display and the drop targets the interactive centre of the product and pushed the grid maths behind them. The layout still adapts to whatever monitors are attached — but only after the user has placed things by hand. 誰も数値フォームを求めていなかった。求めていたのは、自分の画面と、その上の窓の形が見えることだった。だから物理ディスプレイとドロップ先をプロダクトの中心に据え、グリッド計算はその裏へ回した。レイアウトは接続中のモニターに合わせて適合する — ただしユーザーが手で置いたあとに。

The structure 構造

Three steps became one workspace. 3ステップを、ひとつの作業台に。

The old flow was a wizard: three screens in a fixed order, with the actual work crammed into a textarea at the end. Collapsing steps 2 and 3 into a single two-pane workspace let the library and the grid stay on screen together — and moved registration out of the flow entirely, which is what stopped the data loss. 旧フローはウィザードだった。順序の固定された3画面で、実際の作業は最後のテキストエリアに押し込まれていた。Step 2 と 3 を2カラムの作業台にまとめたことで、ライブラリと分割グリッドが同時に見えるようになった。そして登録をフローの外へ出したことが、データ消失を止めた。

Four moves got it there, in order. そこへ至るまでに、4つの手を順に打った。

01
Read the structure out of hand-drawn sketches手書きスケッチから構造を読み出す
Three wireframes I drew by hand fixed the mental model — what sits where, and what dragging is supposed to mean — before any code existed.自分で描いた3枚のワイヤーフレームが、コードより先にメンタルモデルを決めた。何がどこに座り、ドラッグが何を意味するか。
02
Show monitors that actually exist実在するモニターだけを見せる
Names and positions come from chrome.system.display.getInfo(), so the cards match the desk instead of standing in for it.名前と位置は chrome.system.display.getInfo() から取る。カードが机上の代役ではなく、実物と一致する。
03
Let the drop position decideドロップ位置に決めさせる
Dropping on a cell assigns the window; dropping on empty canvas adds a cell. One gesture, two meanings, no mode switch.枠へのドロップは割り付け、余白へのドロップは枠の追加。ひとつの操作に2つの意味を持たせ、モード切替を無くした。
04
Make the last 10% adjustable最後の1割を、あとから直せるように
A ← | → handle on every cell, and a search-or-create dropdown in the header for switching between saved layouts.各枠に ← | → のハンドル、ヘッダーに保存済みレイアウトの検索・新規作成ドロップダウン。

Craft · AI collaboration クラフト · AIとの協働

The AI wrote the grid. It also blocked the app. グリッドはAIが書いた。そして画面を塞いだ。

I had the model build the DOM, the dynamic grid maths in computeDynamicLayout, and the layout-search dropdown, and debug the popup width. What I could not hand over was the rulebook: I redrew the wireframes and specified the interaction rules — accordion editing, drop-on-empty grows the grid, a resize handle per cell — as constraints rather than requests. Three attempts, judged on two things: does it feel direct, and can it lose your data. DOM構築、computeDynamicLayout の動的グリッド計算、レイアウト検索ドロップダウン、そしてポップアップ幅のデバッグはモデルに任せた。渡せなかったのはルールブックのほうだ。ワイヤーフレームを描き直し、インタラクションのルール — アコーディオン編集、空きスペースへのドロップで枠が増えること、枠ごとのリサイズハンドル — を要望ではなく制約として指定した。試したのは3案。判断基準は2つだけ — 直感的か、そしてデータを失いうるか。

Where the model failed モデルが外したところ
A modal that was never closed 閉じられないモーダル
The generated CSS put display: flex straight onto .modal-overlay, which overrides the HTML hidden attribute. Correct-looking code, and the extension opened with the whole screen blocked. The average answer is fluent about CSS and indifferent to what happens on first launch. 生成されたCSSが .modal-overlay に直接 display: flex を書き、HTMLの hidden 属性を打ち消した。見た目は正しいコードで、結果は起動時に画面全域が塞がれた状態。平均解はCSSには流暢だが、初回起動で何が起きるかには無関心だ。
Rejected 01 選ばなかった案 01
A stacked form in the popup ポップアップ内の多段フォーム
By far the least code, and it would have shipped in a day. But the popup is a few hundred pixels wide — the same form that already collapsed there would have collapsed again, and every fix would have been a scrollbar. コード量は圧倒的に少なく、1日で出せた。だがポップアップは幅数百px。すでにそこで潰れていたフォームは、また潰れる。そして直す手段はスクロールバーしか無くなる。
Rejected 02 選ばなかった案 02
Describe the layout in text レイアウトを文章で指示する
Genuinely appealing: CLI-like, one input, no canvas to build. It fails on the one thing this product is about — you cannot picture where a monitor sits relative to another, or which cell a window landed in, from a sentence. 本気で魅力的だった。CLIライクで、入力欄ひとつ、キャンバスを作る必要もない。ただしこのプロダクトの核心で失敗する。モニター同士の位置関係も、ウィンドウがどの枠に入ったかも、文章からは像を結ばない。

Outcomes 成果

No measured numbers yet. 実測値は、まだ無い。

What it did do is remove the re-typing: a developer moving between several monitors and dozens of tabs no longer rebuilds the same list from a text file every time the layout changes. この設計が動かしたのは、再入力の作業だ。複数モニターと大量のタブを行き来する開発者は、レイアウトを変えるたびに同じリストをテキストファイルから組み直さなくてよくなった。

The extension is in release preparation for the Chrome Web Store. Adoption and time-saved figures will be measured after it ships, and this slide will carry them — projected numbers would not be worth reading. 現在 Chrome Web Store の公開準備中。利用状況と削減時間はリリース後に実測し、このスライドに載せる。見込み値を置いても読む価値が無いためだ。

Retrospective 振り返り

Two things this didn't settle. 決着しなかったことが、2つ。

One I fixed and learned from. One I still don't have an answer to. ひとつは直して学んだこと。もうひとつは、まだ答えを持っていないこと。

01
I designed two surfaces and defined the width of one. 2つの表示を作って、幅を決めたのは片方だけだった。
The same markup renders as a popup and as a full page. I styled the full page and let the popup inherit, which is how a missing width on the container turned into a collapsed layout at 800×600. Fixed with an explicit body.as-popup width — but the lesson is that "responsive" was never the problem; an undeclared container was. 同じマークアップがポップアップとフルページの両方で描画される。私はフルページを整え、ポップアップには継承させた。その結果、コンテナの幅指定が抜けていたことが 800×600 でのレイアウト崩れになった。body.as-popup に明示的な幅を置いて直したが、教訓は「レスポンシブが問題だったのではなく、宣言されていないコンテナが問題だった」ということだ。
02
Past sixteen cells, the labels stop being readable. 16分割を超えると、ラベルが読めなくなる。
The grid keeps subdividing happily; the URL inside each virtual card does not. Truncating, showing favicons, or refusing to split further are all defensible, and I don't yet know which one is right — so the current build simply lets it get small. グリッドはいくらでも細かく割れるが、仮想カードの中のURLはそうはいかない。切り詰める、ファビコンだけにする、それ以上割らせない — どれも筋は通り、どれが正解かはまだ分からない。だから現状は、小さくなるに任せている。

The takeaway この仕事から

Let people place it, and the numbers stop mattering. 置けるようにすれば、数値は要らなくなる。
